# Nexxi development rules

- Use PHP WordPress classic templates, semantic HTML, Tailwind CSS, Alpine.js, and minimal vanilla JavaScript. Node.js is for development and asset builds only. Do not add React, Vue, Next.js, a page builder requirement, a separate backend, database, or API.
- Keep application changes inside `wp-content/themes/nexxi-theme/` and `wp-content/plugins/nexxi-core/`. Root files may cover documentation, Git, build, tests, and deployment. Never edit WordPress Core, WooCommerce Core, third party plugins, production data, or hosting configuration without explicit authorization.
- The theme owns presentation. The plugin owns only requested Nexxi business behavior; do not add speculative functionality. Keep PHP templates small and use reusable parts as the interface grows.
- Integrate WooCommerce through official PHP APIs, product objects, hooks, filters, and templates. Declare theme support. Check plugin availability before invoking WooCommerce functions. Prefer hooks and filters to template overrides. Preserve WooCommerce cart, variations, checkout, orders, stock, and payments. Determine whether checkout uses Blocks or classic templates before customizing it.
- Use Tailwind utilities and shared tokens in `src/css/app.css`; reserve custom CSS for needs utilities cannot express. Bundle Alpine.js locally and use it only for lightweight presentation. Do not replace WooCommerce behavior with Alpine state. Avoid unnecessary packages and pin dependencies in `package-lock.json`.
- Follow WordPress Coding Standards. Escape output, sanitize and validate input, use nonces and capability checks for relevant actions, and use WordPress APIs. Avoid hardcoded site URLs, secrets, customer data, and duplicate SEO metadata. Keep semantic structure, keyboard access, visible focus, responsive images, and performance in mind.
- After PHP changes, check syntax. After frontend changes, run `npm ci` when dependencies change and `npm run build`; inspect the generated assets. Run meaningful tests available for the changed behavior. Report any WordPress/WooCommerce integration that could not be exercised locally.
- Keep `node_modules`, uploads, databases, secrets, WordPress Core, WooCommerce Core, and third party plugins out of Git. Commit the lockfile and production assets. Preserve unrelated changes. The project owner authorizes Codex to commit, push, and merge completed development tasks into `main` after relevant checks without requesting separate approval each time. Open or update a Pull Request when GitHub API access is available; otherwise use a safe Git merge and push. Never force-push, bypass branch protection, or deploy to production. Report access blockers precisely.
- For Mắt Bão deployment, package only the custom theme and plugin with built assets. Do not require Node.js on hosting. Test on staging, check PHP/WordPress/WooCommerce versions, and obtain approval before production access, deployment, or configuration changes.
